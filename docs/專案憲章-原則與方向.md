# Wundadi 專案憲章：原則與方向（AI／開發必讀）

> **用途**：換 Model、開新對話、Open Canvas 之前，先讀本文件。  
> **地位**：產品決策與功能畫線的權威摘要；細節契約另見文末「相關文件」。  
> **維護**：原則變更時必須改本檔，並同步 `.cursor/rules/`。

---

## 1. 北極星

- **Wundadi**＝獨立 **SMART on FHIR** 醫療系統，最終**全面取代醫聖**看診／申報（非鎖死單一廠商）。
- **資料權在診所端**：病歷與營運資料以本機／院所可控為主；雲端是同步與備援，不是「診所什麼都不知道、廠商代操一切」。
- 現行 repo＝**新核心**（三沙盒、門診閉環、Pack、申報模組）；與願景無衝突。

## 2. 一人公司怎麼活（商業與客服邊界）

### 2.1 要打掉的模式

- 診所端不看公告、不看計畫，只負責「收錢」；中間一大截給廠商／顧問當客服與代操。
- 產品做成「每個新健保專案一鍵達標／保證指標」→ 等於無限客服，一人公司必死。
- 假指標、帳面符合即可的文化：不主動加速；標準產品**不賣**「保證過關」。

### 2.2 要促成的模式

- **常用主幹**：產品做好、算得準、退件可診斷。
- **時令專案／計畫**：診所（或資訊）自己讀懂條件；系統＋ **Cursor** 當工具（找人、組檔）；**VPN 網頁上傳與是否重複由人確認**。
- AI 普及後，希望變薄的是「看不懂所以外包」那層抽成，不是讓診所更可以無知。

### 2.3 客戶前提

- 使用本軟體的院所，需有 **Cursor（或同等）對本專案自助**的覺悟。
- 開啟：`開啟-用Cursor問本專案.bat` → Cursor 打開本 repo → **有問題先問這裡**（規則已內建）。
- 只想「全包代操、什麼都不用懂」→ **非服務對象**（可另案報價，不進標準月費／客服）。

## 3. 功能分層（做任何功能前先判）

| 層 | 名稱 | 做什麼 | 不做什麼 |
|----|------|--------|----------|
| **A** | 主幹 | 產品內建、常態維護、有驗收 | 不塞時令計畫黑箱 |
| **B** | 工具 | 查名單、匯出、依**當次**格式組檔、回執可讀 | 不保證指標；不代讀所有公告 |
| **C** | 不接／另案 | — | VPN 自動點選、一鍵收案到成功、保證達標、無限專案客服 |

### 3.1 判題（五問）

1. 沒它，診所**每週**會痛嗎？→ 高＝偏 A。  
2. 誰必須讀懂規則才算對？→ 計畫條文＝診所。  
3. 輸出是否「依公開／院所指定格式組檔」？→ 是＝B；「我們幫你保證分數」＝越界。  
4. 失敗誰被叫醒？→ 格式／主幹錯可進產品診斷；「條件解讀錯」不開你的無限客服票。  
5. 會不會讓診所更可以不看公告？→ 會＝不要做進標準 A。

### 3.2 例子

- **月申報、藥價 Pack、門診閉環、讀卡** → **A**。  
- **家醫群組收案、各種時令上傳** → **B**（Cursor 讀公文＋找人＋組檔；人上 VPN）。  
- **自動登健保 VPN 網頁收到沒重複為止** → **C**（無 API、網頁改版＝惡夢；人工反而簡單）。

## 4. 健保更新與對接

### 4.1 更新口要單一

- **規則／藥價／格式參考資料**：Hub 發布 Pack → Spoke `/sync/packages` Hydrate（無感；失敗 fallback；**人只被事件叫醒**，禁止月例行審核通知）。
- **程式本體**：整包置換為主（不可變發行），不是碎片補丁；檢查更新可另做，與 Pack 分線。
- 對診所來說「更新」應感覺單純；對維運，Hub 可多個資料源，但**進站口仍是 Pack**。

### 4.2 什麼常改、什麼少改

- **藥價／用藥品項**：開放資料、約月更 → Hub 已做（datastore，非爬 HTML）。  
- **管制藥品分級**：食藥署開放資料（未註銷藥證＋銷售一覽表）併入同一 Pack；**不是**健保專網保險對象查詢。  
- **申報 XML 主幹**：多年相對穩定 → **一次做成正式模組**；不是因為常改才對表，是因為我們還在過渡格式。  
- **給付規定**：多為病歷理由／抽審；診所預設**不做給付警察**（重疊用藥等客觀檢查除外）。  
- **特材／診療**：表格式可走 Pack；皮膚／家醫體感常較少。  
- **轉診、檢驗上傳等**：屬對接家族；應用 **共用 NHI Gateway 思維**（連線／組檔／回執殼＋交易類型），不要每個從零做一個軟體；頻率決定進 A 或 B。同一條轉診上傳（種類 10 轉出、04 回覆）與論質檢驗（種類 26）走 `C:\NHI\SAM\COMX1` 的雲端 SAM。看診這台打開門診或掛號時，同時打開讀卡軟體 6.0 與上傳轉診用的 5.1.7。6.0 佔讀卡機。5.1.7 必須先確認讀卡機屏蔽已在 `C:\NHI\BIN`，沒有屏蔽就不啟動。門診視窗都關掉時，兩支一起關。大廳「工具／讀卡並存測試」確認 6.0、讀卡機、閹過的 5.1.7 與雲端元件同時成立。測試不送出病人資料。真正送出仍是轉診名單與論質那一筆。

### 4.3 申報模組（主角之一）

- 位置：`src/claims/`＝**組檔唯一出口**。  
- 已做：天數／量／開藥當下 Pack 單價快照；統計與匯出走模組；過渡 XML `wundadi-claims-v0`。  
- 待做：換成**署方門診申報正式結構**（KAN-6）；格式穩＝更該一次做對。  
- 門診臨床主幹（Encounter／Condition／MedicationRequest）已通；缺的是計價欄位與正式 XML（計價接線已補一輪）。

### 4.4 Hub–Spoke 人力契約（摘要）

- 機器可排程；通過則靜默 Publish／Hydrate。  
- 人只在：實質出入、BUG、無法判定、拉檔失敗等**事件**被叫。  
- Spoke：不爬、不做 LLM、不為更新重啟。  
- 詳見：`docs/Hub-Spoke無感更新與人力介入契約.md`。

## 5. Cursor 在產品裡的角色

- **開發者／院所時令專案**：Cursor 開本專案＝預設工作台。  
- Agent 協助 B 層時：讀使用者提供的公文 → 摘要條件 → 可重跑找人 → 依**本次**格式組檔 → **禁止**實作 VPN 自動上傳。  
- **不要**把「內建半套 Cursor／貼公文一鍵收案引擎」當標準產品目標；難度與客服成本通常高於「客戶裝 Cursor」。  
- 規則：`.cursor/rules/clinic-cursor-self-serve.mdc`、`.cursor/rules/wundadi-product-vision.mdc`。  
- 說明：`docs/診所端-用Cursor處理時令專案.md`。

## 6. 資料與臨床產品原則（已定）

- 病歷／Media：**禁止 DELETE**，僅 POST／PUT（KAN-25）。  
- **修改必留痕**：正式**資料庫上線**後啟用（`audit_recording=1`）。啟用當下可清空上線前測試／匯入噪音；之後凡影子庫寫入必寫 `audit_modifications`（哪台電腦、時間、改了哪一欄）。內網不驗證身分、不要求 PIN。上線前預設**不寫**稽核列，避免把匯入過程記進去。切點：`scripts/tools/正式上線-啟用修改稽核.bat`。每台電腦的名稱在院所資料的「本機工作站」顯示名稱。  
- 醫美知識庫：**不魔改 UI**；只做資料對接 Adapter（KAN-24，待規格）。  
- 診所面向：高單價／給付章節**預設不跳窗**；用藥重疊等客觀檢查可保留。  
- 「抽審沒抽到就過」是現場現實之一；產品高標準＝**客觀層幾乎不因系統而錯**，不是承諾零核刪。

## 8. 給下一個 Model／Canvas 的強制指令

1. 變更產品行為或新功能前，重讀**本憲章**、`docs/交接-目前進度.md` 與功能分層 A/B/C。近期已定的掛號、身分優待、押金、問診、主機／工作站，不要重做或改回去。  
2. 不要把時令專案做成標準內建「保證達標」。  
3. 不要實作健保 VPN 網頁自動化。  
4. 申報／對接新交易：優先擴 `src/claims/` 或未來的共用 gateway，保持**單一組檔／對接口徑**。申報現況先讀 `docs/申報接手說明.md`，不要把 `Z:\SC`、醫聖程式、全部健保 PDF 重讀一遍。  
5. 藥價／參考資料更新走 Pack；與臨床出站 `/sync/queue` 分離。  
6. 原則若與程式衝突：先改程式或先改憲章並註明，禁止默默偏離。
