🧱 模組一（Phase 1）｜去中心化身分驗證核心 【Jira: KAN-1｜M1-FIDO2】
================================================================================
目的：拋棄中央帳密庫，利用密碼學硬體與生物特徵建立不可否認的臨床身分對帳機制。

1. 前端 WebAuthn API 呼叫組件
[ ] 實作 navigator.credentials.create() (註冊模組)
[ ] 後端隨機挑戰碼（Challenge）必須為安全性強的 32 Bytes ArrayBuffer。
[ ] rp.id 強制綁定醫院內部網域（防範中間人與網頁釣魚攻擊）。
[ ] user.id 採用內部 Patient UUID，且必須進行 Base64URL 編碼。
[ ] pubKeyCredParams 寫死 alg: -7 (ECDSA w/ SHA-256) 與 alg: -257 (RSA w/ SHA-256)。
[ ] authenticatorSelection 的 authenticatorAttachment 設為 cross-platform（強制感應晶片卡/硬體金鑰）或 platform（本機刷臉/指紋）。
[ ] 實作 navigator.credentials.get() (登入/驗證模組)
[ ] 前端取得 Assertion 後，必須精準擷取 credential.rawId、authenticatorData、clientDataJSON 與 signature，並轉為 Base64 格式上傳。

2. 後端 WebAuthn 驗證器與 FHIR 資料庫儲存
[ ] 引入開源驗證庫： Python 專案引入 py_webauthn 或 Node.js 專案引入 @simplewebauthn/server。
[ ] 實作 FHIR Patient 資源結構擴充 (Extension Definition)
[ ] 定義 Profile：https://wundadi.tw/fhir/StructureDefinition/patient-fido2-key。
[ ] 欄位 1：keyId (valueString) ➔ 儲存 WebAuthn 的 Credential ID。
[ ] 欄位 2：publicKey (valueString) ➔ 儲存 COSE 格式轉 PEM 的公鑰字串。
[ ] 欄位 3：counter (valueInteger) ➔ 儲存計數器，防止重放攻擊（Replay Attack）。
[ ] 撰寫對帳邏輯：比對前端傳回的 Signature，驗證成功後，自動更新該 Patient 資源內的 counter 數值。

3. SMART on FHIR 安全憑證發放器 (OAuth 2.0 / JWT)
[ ] 開發獨立 Token 授權伺服器端點： POST /oauth/token。
[ ] 實作 JWT (JSON Web Token) 簽發機制：
[ ] 簽章演算法：強制採用非對稱加密 RS256。
[ ] Claims 欄位：iss (發行者網址)、sub (格式為 Patient/[UUID] 或 Practitioner/[UUID])、iat (簽發時間)、exp (iat + 14400秒，嚴格四小時過期)。
[ ] Scopes 權限微粒化控制：嚴格遵循 SMART on FHIR 規範（例如：user/AllergyIntolerance.write, patient/Observation.read）。

👥 模組二（Phase 6）｜個人主權社交恢復外掛 【Jira: KAN-9 Epic】
================================================================================
目的：落實個體自負責任，金鑰弄丟時不需要政府或萬能後台，由信任的群體自主縫合。
依賴：模組一（FIDO2）完成後再開。注意：≠ Jira M2/KAN-2（那是模組零基礎建設）。

1. 密鑰切片演算法核心 (Shamir's Secret Sharing)
[ ] 後端引入密碼學套件： Python secretsharing 或 C# ShamirSecretSharing 庫。
[ ] 實作 (2, 3) 門檻值切片邏輯：當病人註冊時，系統動態生成身分 Master Key，自動切割為 3 個碎片，設定任 2 片可還原（Threshold = 2, Total Shares = 3）。
[ ] 實作碎片非對稱加密分發 Pipeline：
[ ] 碎片 A ➔ 用「診所/醫院機構憑證公鑰」加密 ➔ 存入本地伺服器。
[ ] 碎片 B ➔ 用「指定家屬 FIDO2 公鑰」加密 ➔ 推送至家屬 App。
[ ] 碎片 C ➔ 用「信任的第三方醫學中心公鑰」加密 ➔ 跨院拋送儲存。

2. 金鑰還原與帳號重置 API 規格
[ ] 開發重組端點： POST /api/v1/identity/recovery-recombine。
[ ] 實作碎片收集狀態機：
[ ] 驗證提交者的數位簽章（確認是診所端人工核對雙證件後釋出、或是家屬點擊 App 釋出）。
[ ] 收集滿 2 個合法碎片後，調用還原函數，解鎖 Master Key。
[ ] 覆寫資料庫中該 Patient 的舊 Extension.publicKey，完成金鑰更換，舊金鑰全網作廢。

[ ] 實作標準 FHIR AuditEvent 唯讀寫入：
[ ] 包含欄位：recorded (時間戳記)、agent (包含操作醫生與聯署護理師的 ID)、source (實體急診電腦名稱)、entity (被讀取的病人 ID 與破窗原因)。
[ ] 實作硬體死鎖：利用 AWS S3 Object Lock（合規模式）或在地具有 WORM（一寫多讀）技術的 NAS 儲存此 JSON，確保連資料庫最高管理員（DBA）也無法修改或刪除此軌跡。

🧼 模組五（Phase 3a）｜AI 數據清洗與冷啟動中間件 【Jira: KAN-5｜M5-AI清洗】
================================================================================
目的：在上線初期解決荒漠困境，利用大語言模型將歷史純文字垃圾清洗為高價值 FHIR 資源。
依賴：模組四 §1（Allergy Profile、verificationStatus 寫入規則）。

1. 舊系統文字與雲端藥歷 Ingestion Pipeline
[ ] 撰寫日誌/歷史病歷批次讀取器：從舊資料庫或健保雲端下載近期的純文字備忘錄（TXT/串流）。
[ ] 串接 Gemini API 結構化輸出功能 (Structured Outputs / JSON Schema)
[ ] 設定嚴格的 Pydantic (Python) 或 JSON Schema。
[ ] 限制輸出欄位必須包含：snomed_allergy_code, rxnorm_substance_code, snomed_manifestation_code。
[ ] 撰寫系統 Prompt 範本：
你是一個精準的醫療資訊數據清洗專家。請閱讀以下舊 HIS 系統混亂的手寫過敏備忘錄，
將其完全轉譯為標準的醫學國際代碼。如果文字提及某種特定藥名，請找出其 RxNorm 成分碼；
如果提及症狀，請轉為 SNOMED 代碼。必須嚴格遵循提供的 JSON Schema 輸出，不得包含任何額外推論文字。

2. 資料驗證與防腐閘門 (Data Validator)
[ ] 實作寫入攔截器 (Interceptor)：當清洗後的資料要寫入新 FHIR 資料庫時，檢查 coding.code 欄位是否為空。
[ ] 硬性規定：任何無法成功轉譯為國際標準代碼（即只有 Text、沒有 Code）的歷史資料，一律強制將 verificationStatus 設為 "unconfirmed"，且禁止與常規開藥系統進行自動阻斷連動，防止垃圾互相污染。

2. 「掛號快」＝本機主控台 API 讀基本資料＋VPN 取號等，不再等整段慢速寫卡。
3. 「不用特別寫進健保卡」＝不必再把就診明細寫進晶片；仍要把就醫寫進署方雲端（取號／WriteCode 等），不是「什麼都不寫」。
